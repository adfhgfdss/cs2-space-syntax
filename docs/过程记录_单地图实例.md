# 单地图实例：过程记录

地图：**de_mirage**
目标：为报告中的空间句法实例，产出可用的行为数据层（击杀分布 + 开局占位），
并验证数据管道的正确性。

---

## 一、需要拿到哪些数据，为什么

空间句法分析要用两组数据对照：

| 数据 | 用途 | 来源 |
|---|---|---|
| 地图雷达图（俯视图） | 画 VGA 图、叠加热力图的底图 | CS2 游戏文件 |
| overview 坐标文件 | 世界坐标 ↔ 像素的变换参数 | CS2 游戏文件 |
| demo 事件数据 | 击杀位置、玩家位置 | 比赛录像 |
| 整合度 / 选择度 | 构形指标 | depthmapX 计算（下一步） |

关键在第二项。CS2 的坐标变换是：

```
radar_x = (world_x - pos_x) / scale
radar_y = (pos_y - world_y) / scale        # 注意 Y 轴反向
```

de_mirage 的参数为 `pos_x=-3230`、`pos_y=1713`、`scale=5.00`，雷达图 1024×1024。

## 三、执行步骤

### 步骤 1：拿到 radar 图和 overview 文件

官方途径是用 Source2Viewer-CLI 从本地 CS2 的 `pak01_dir.vpk` 里抽：

- radar 图：`panorama/images/overheadmaps/*_radar_psd.vtex_c`
- 坐标文件：`resource/overviews/*.txt`

本机 GitHub release 附件下载被重置，改用现成镜像
`2mlml/cs2-radar-images` 取得 `de_mirage.png` 与 `de_mirage.txt`。

### 步骤 2：验证镜像与本地游戏版本是否一致

这一步决定了要不要回头去搞 Source2Viewer。overview 文件是纯文本，VPK 是公开
格式，所以写了个最小 VPK v2 读取器直接把游戏里那份抠出来对比：

```
.venv\Scripts\python.exe vpk_extract.py "...\game\csgo\pak01_dir.vpk" "overviews/de_mirage" data\game_original
```

结果：`resource/overviews/de_mirage.txt` 位于 pak 022，640 字节。
与镜像版本做 SHA256 比对 —— **逐字节完全相同**。

结论：坐标变换参数是权威的，不需要 Source2Viewer。

### 步骤 3：提取 demo 事件

```
.venv\Scripts\python.exe extract_events.py demos/test_demo.dem
```

得到 73 次击杀（含攻守双方世界坐标）、10 个回合的 start / end / freeze_end
事件，落盘为 parquet。

### 步骤 4：验证坐标映射

两个独立的检验：

**检验 A —— 出生点一致性。** 回合开始时玩家必定站在出生点上，而 overview
文件里写了出生点在雷达图上的归一化坐标。取每回合 freeze_end 之后 64 tick
（1 秒）的位置求队伍质心，与声明的出生点比对：

| 队伍 | 样本数 | 解析质心（雷达像素） | 声明出生点 | 偏差 |
|---|---|---|---|---|
| CT | 45 | (311.0, 722.9) | (287, 717) | 25.0 px |
| T | 45 | (894.3, 350.5) | (891, 369) | 18.4 px |

偏差换算成游戏距离约 90–125 单位，符合"开局一秒后队员从出生点散开"的预期。
若雷达图与坐标文件不配对、或 Y 轴方向弄反，偏差会是数百像素。

**检验 B —— 落点覆盖率。** 雷达图上地图只占画布的一部分（有内容的像素仅
占 29.9%）。如果映射正确，击杀点应当全部落在有内容的区域：

```
有内容的像素        : 29.9%
落在有内容区的击杀  : 73/73 (100.0%)
```

若雷达图是别的版本，随机命中的期望值约 30%，73 个点全中的概率约 0.3^73，
实际上不可能发生。

### 步骤 5：分层出图与导出

```
.venv\Scripts\python.exe analyse_map.py
.venv\Scripts\python.exe summarise_grid.py
```

按阵营分层，因为 CT 和 T 在同一套几何上目标完全不同，混在一起会把两种运动
逻辑平均掉。

### 网格统计

1024px 画面按 16×16 切分，每格 64px（约 320 游戏单位，接近一个门洞尺度）。

- 256 格中，42 格出现过击杀，105 格出现过玩家占位
- 占位最高的格子呈极强的单边性：

| 格子 (列,行) | 占位样本 CT | 占位样本 T |
|---|---|---|
| (13, 4) | 0 | 116 |
| (12, 3) | 0 | 112 |
| (5, 8) | 102 | 0 |
| (11, 5) | 0 | 95 |

- 开局 15 秒内的区域重叠：

| | 格数 |
|---|---|
| 仅 CT 到过 | 48 |
| 仅 T 到过 | 51 |
| 双方都到过 | 6 |

即开局阶段双方活动范围几乎完全不重叠（105 个被访问格子中只有 6 个重叠）。
这是本实例中最值得在报告里讨论的一个量化结果——它说明 Mirage 的开局结构
具有强分离性，这一点可以直接与构形指标对照。

## 五、局限（写进报告时必须说明）

1. **样本量极小。** 仅 1 场 demo、10 个回合、73 次击杀。本文所有数字是管道
   演示，不具备统计效力，不能用于推断地图的普遍规律。
2. **demo 来源为路人匹配**，不是职业比赛。路人局的战术纪律性低于职业赛，
   但正因如此更接近"自然运动"假设的适用条件。
3. **雷达图来自社区镜像。** 其 overview 文件已与本地游戏逐字节比对一致，
   但雷达图本身是编译纹理，未做逐字节校验，仅通过落点覆盖率（100%）间接
   验证。
4. **时间窗口的选择是主观的。** 15 秒是本研究设定的"战术尚未展开"的经验
   阈值，换一个窗口数值会变。
5. **空间句法计算的几何是未被打乱的原始空间**，而实战中烟雾和火焰会临时
   切断视线。这一假设边界需要在报告中明确写出。

## 七、2026-09-19 增补：不做手工描图，改用游戏自带的导航网格

上面的"下一步"在第 1 步就卡住了：depthmapX 需要把墙手工描到图上，而 CS2 是
多层三维空间，手工描图既慢又不可复现。当天换了一条路，并且把 de_dust2
（没有 demo 的那张图）也一起解决了。完整方法与结果见 **`SPACE_SYNTAX.md`**，
这里只记过程要点。

### 7.1 找到权威的"可通行空间"

本地 CS2 的每一张官方地图都是一个独立地图包：
`game/csgo/maps/de_dust2.vpk`，里面含 `maps/de_dust2.nav`（481,872 字节）。
这是 Valve 自己烘培的导航网格，每个顶点都是世界坐标，等价于人工描图但权威
且可复现。`nav_extract.py` 负责把它抽出来。

### 7.2 版本 36 需要自己解析

awpy 2.0.2 自带的 `.nav` 解析器只支持版本号 30–35，读到 36 直接抛
`Unsupported nav version: 36`。于是自己定位结构：

* 头部 145 字节；`+145` 是角点数（3015），随后是角点坐标；
* 接着是多边形数（2242）和多边形索引表；
* 定位方式不是硬编码偏移，而是扫描"u32 计数 + 一段干净的坐标浮点数 +
  索引全部自洽"的候选，换地图也不会失效。

### 7.3 rotate=1 的歧义用数据自己判

de_mirage 的 overview 写 `rotate=0`，de_dust2 写 `rotate=1`。与其照抄社区
约定，不如把 8 种"轴向对调 + 翻转"组合都试一遍，看哪种能让导航网格落在
雷达图有内容区内的比例最高：

| 地图 | 标准式 | 次优组合 |
|---|---|---|
| de_dust2 | **100.0%** | 71.3% |
| de_mirage | **99.5%** | 60.5% |

结论是这两张镜像雷达图都已经是"和 overview 归一化坐标一致"的方向，
`rotate=1` 不需要额外对调。这一步同时验证了坐标变换和导航网格解析。

### 7.4 VGA 自己实现

`space_syntax.py`：16 px 栅格 → "不可通行 = 墙" → 格心射线求可见性图 →
连通度 / 等视域面积 / 整合度（拓扑与米制两种距离）/ 选择度（介数中心性）。

* de_dust2：2,041 个可通行格子，163 s 跑完；
* de_mirage：1,386 个格子，67 s 跑完。

### 7.5 与行为数据对照（de_mirage）

`extract_tracks.py` 抽出 10 个回合、25,626 个玩家位置采样（每 0.25 s 一个），
`analyse_behaviour.py` 把它们映射到同一套格子：

* 99.89% 的轨迹点落在导航网格内（第 4 节那两个检验之外的第三个独立验证）；
* 相关分析：**经典运动经济假设不成立**。全回合占位 vs 拓扑整合度 ρ=+0.047，
  开局 15 秒占位 vs 拓扑整合度 ρ=−0.185；分阵营后 CT 占位 vs 连通度 +0.263、
  T 占位 −0.015。

这条负结果在 `SPACE_SYNTAX.md` 第 8 节做了讨论（任务驱动 + 对抗驱动的移动
逻辑、占位≠运动、攻守逻辑相反、可见性是风险而非收益）。样本量仍然极小，
所以只作管道演示。

### 7.8 实现自检：合成形状救了选择度

自实现的 VGA 不能只靠"公式抄对了"取信。`test_space_syntax.py` 用 5 个答案
已知的假想平面跑回归测试：空房间、直走廊、十字走廊、L 形走廊、双房间带单格
门洞，各自断言连通度、整合度方向、选择度峰值位置。

第一版测试就抓出一个真错误：**直走廊（任意两格都互相可见）竟算出非零的选择度**。
定位到 Brandes 算法的依赖累加阶段把"同层邻居"也当成了后继，导致重复计数；
修正后完全图上的选择度正确归零（凸空间里不存在"中间点"，选择度必然是 0）。
修完重新跑了两张图的句法层与相关分析，`out/` 里的数字全部是修正后的版本。

顺带记录一个**公式退化情形**：当某格与其他所有格子都互相可见时 MD=1，
Hillier & Hanson 的 RA=2(MD−1)/(n−2)=0，整合度发散为 ∞。真实地图只要有遮挡
就不会出现，但解释极端值时要知道。

### 7.9 研究范围的两次调整：先收敛单图，再改回双图

对两张图做了一次数据盘点（`data_inventory.py`，结论写在 `数据盘点.md`）：

* 几何层：de_dust2 可通行面积 2,746 m²、2,041 个格子；de_mirage 2,123 m²、
  1,386 个格子——**dust2 大 29%–47%**；
* 行为层：de_mirage 有 1 场 demo / 10 回合 / 73 击杀 / 25,626 个轨迹采样 /
  7,627 次格间移动 / 覆盖 75.8% 的可通行格子；**de_dust2 全为 0**。

据此我先把研究收敛为单图 de_mirage（dust2 的几何与两图对照降级到
`out\appendix_dust2\`）。**随后（同一天下午）决定改回双图对比**——因为研究问题
本身就是"两张地图的构形与行为对照"，缺的那一边应当补齐而不是砍掉。于是：

* 文件搬回 `out\`，`appendix_dust2\` 目录清空；
* 文档恢复双图口径（`SPACE_SYNTAX.md` 的"结果 A / B / C"）；
* 新增 `ingest_demos.py`（多 demo、多地图批量摄入，行为数据按地图分表）；
* `run_all.py` 支持 `--demos`，**没有 demo 的地图自动跳过行为层**；
* 缺口与获取路径整理成 `数据获取.md`。

两次调整都在 `_history\` 里有快照（收敛版 ≈ 快照 103 之前，双图版在其后），
随时可以回看或回滚。**这段"先收敛后扩张"的决策过程本身也是方法章节的素材**：
数据可得性决定可行性，而研究问题决定范围。
